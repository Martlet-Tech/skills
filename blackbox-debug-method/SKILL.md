# 黑盒调试方法论 —— 一次真实复盘

> ## ⚠️ 使用说明（请先读这一段）
>
> **这份文档不适合作为 skill 加载给智能体使用。**
>
> 原因：它记录的是**一次具体事件的推理过程**，包含大量只在那个语境下成立的判断。
> 作为提示词注入时，"先测绘再理论""反相关是签名"这类凝练表述会占用很高的注意力权重，
> 但它们**缺少边界条件**——什么情况下不适用、需要多少成本、失败了该怎么退。
> 智能体拿到这些句子，很可能在完全不同的场景里生搬硬套。
>
> 调试能力需要的是**具体的技术事实**（寄存器怎么读、哪个量是截断的、什么现象对应什么机制），
> 那些已经整理进 `esp32p4-dsi-debug`。方法论是**从事实里长出来的**，
> 直接抽取结论会丢掉让它成立的土壤。
>
> 所以：**这份当经验记录看，不要装。**

---

## 一、事情的起点

一块 ESP32-P4 板子，480×800 的 TDDI 屏（ILI9883C-X1），显示画面被扭成若干段斜线。
同一块屏在另一块 STM32 板（走 SSD2828 那颗 DPI 桥）上显示正常。

两边的初始化命令**字节级完全一致**（175 条，程序化比对，零差异）。
时序、lane 数、像素格式也都一样。

于是问题变成：**同样一份配置，为什么一边好一边坏？**

---

## 二、我（AI）走错的六轮

现在回看，每一轮的错误都不在"想错了一个机制"，而在**实验方法**。
把过程摊开，比结论更有用。

### 第 1 轮：burst vs non-burst

**假设**：TEST10 那边是非突发模式，P4 是突发模式，差异在此。

**做法**：改 `dsi_ll_set_video_burst_type()`，在 `esp_lcd_panel_init()` 之后调用。

**结果**：画面"一点差异都没发生"。

**错在哪**：`vid_mode_cfg` 是 R/W 寄存器，但硬件有影子寄存器，
需要 video mode 使能时重载。我在**已经使能之后**才写，很可能从未生效。
而且当时没有可靠的"是否生效"判据——**这一点让整个实验变成无效实验**。

**教训**：`改了没变化` 有两种解释，`假设错了` 和 `改动没生效`。
分不清这两种，实验就是白做。**每个实验必须自带生效旁证。**

### 第 2 轮：hline 截断误差

**假设**：`ratio = lane/dpi/8` 用整数算，导致 hline 有偏差。

**做法**：算出真值 907 vs IDF 写的 913，改成 907。

**结果**：毫无变化。

**错在哪**：方向对了一半（确实是截断问题），但当时用的参数本身是错的
（我以为 lane=432，实际是 1000），算出来的 907 不是真值。
**而且我把"推算出的斜线条数"当成了验证** ——"算出 5.1 条，看到 5 条，吻合"。

**教训**：数值凑上不等于因果。这次之后我又犯了两次同样的错（见第四节）。

### 第 3 轮：VID_NUM_CHUNKS

**假设**：TRM 给了带宽匹配方程，解出 `VID_NUM_CHUNKS` 应为 1.25，
而 IDF 写的是 0，所以改成 1。

**结果**：错误率从 23.31% 变成 23.33%。**完全没变。**

然后又试 2（方向相反的配置），23.29%。**还是没变。**

**这一轮反而是有价值的**：两个方向都试，把 `chunk 划分` 这条线**彻底排除**了。

**教训**：反向对照（一个快 20%、一个慢 59%）能干净地切掉一整条假设线。
这比单点实验的信息量高。

### 第 4 轮：FIFO 溢出

**假设**：`dpi_pld_wr_err` 每行都报，应该是 DPI 写入 FIFO 溢出。

**做法**：加 FIFO 实时状态采样。

**结果**：`dpi_pld_w_full` **恒为 0**，从来没溢出过。
而正常配置和异常配置的 FIFO 水位虽然有差异，但**都没有越界**。

**错在哪**：我把一个"每行都出现的伴生信号"当成了病因。
后来发现正常配置下它也是每行一次。

**教训**：一个信号在正常和异常情况下**都存在**，它就不是判据。
要先确认"这个量在健康状态下是什么值"。

### 第 5 轮：行末余量

**假设**：21 好 22 坏，可能因为 21 的余量更大（+7.14% vs +3.45%）。
于是只把 `VID_HLINE_TIME` 拉长 5%。

**结果**：**变成了另一种坏法**——每行固定左移 16~32px，连续歪斜、看不出分段。

**错在哪**：`VID_HLINE_TIME` 不是"行总长"这么简单，它还隐含定义了行内各段的相对位置。
单独拉长会让有效像素区在行内的位置漂移。

**教训**：改一个参数前，先确认它在系统里**参与了哪些约束**。
这个参数同时是"总长"和"分段基准"，只满足一个就会破坏另一个。

### 第 6 轮（用户指令）：只改速率

**用户的判断**：「量不能改，porch、VFP 这些都不该改，尽管我实验时在改它。
可以改的是**做事情的速度**，也就是 FIFO 写入读取的速度。」

**这个约束一击命中。**

因为它把整个旋钮空间切成两类，然后冻结一类。之后：

```
ratio = lane / dpi_real / 8
hline = HTOTAL * ratio
byteclk = lane / 8
=> hline/byteclk = HTOTAL / dpi_real    ← 与 lane 无关
```

所以改 lane **不改变任何时序量**，只改变 `byteclk` 和 `ratio` 的取整情况。
搜索从"二维乱撞"变成"一维扫描"。

取 `lane = 480` 使 `ratio = 480/30/8 = 2.000000` 精确整数，
四段零截断，画面正常。**问题解决。**

## 三、用户的两次关键动作

抛开我的分析，整个过程中真正推动事情的是两个动作。

### 动作一：单轴扫描，而不是假设检验

用户把 VFP 从 16 扫到 166，然后报出：

> 「vfp>140 触屏才好使；vfp<=21 的时候显示才好使，22 都不行。」

**为什么这个动作价值最高：**

我前面六轮，每轮都是"押一个假设 → 改 → 看结果"，每次得到 **0 或 1 个比特**。
用户做的是**扫描**，一次投入得到一整条响应曲线，而且**找到了不连续点**。

在单次实验成本很高（build + flash + 肉眼确认，10~30 分钟）的场景下，
这个差异是数量级的：同样的成本，一个换 1 bit，一个换一整条曲线。

**更关键的是：那个不连续点本身就是信息。**

---

### 动作二：把旋钮分成两类，冻结一类

「只改速度相关，不改时序值。」

这是一个**约束**，不是一个假设。它的作用不是指出答案，而是**缩小搜索空间**。

原来的状态是我在"时序量"和"速率"之间来回乱试，每次改一个，归因困难。
有了约束之后，所有的实验都在同一维度上，结果可以互相比较。

**而且它恰好指向了病因所在的维度。**

---

## 四、那个断点为什么是关键 —— 事后才知道的

21 好、22 坏。当时没人知道为什么。

后来算清楚：

```
VFP=21: 总行 839 -> 宏值 576*839*60/1e6 = 28.996 -> int 28 -> div=240/28=8 -> 真实 30.0000
VFP=22: 总行 840 -> 宏值 576*840*60/1e6 = 29.030 -> int 29 -> div=240/29=8 -> 真实 30.0000
```

**两者的真实 DPI 时钟完全一样。**

因为 `240/28` 和 `240/29` 在整数除法下**都等于 8**。
变的只有 `LANE = 宏值 × 16`（448 → 464）。

> **这个断点是编译期整数除法的产物，不对应任何物理量。**

由此得到一条可复用的判据：

> **物理系统不会在 21 和 22 之间突然坏掉。整数边界会。**
> 看到响应在"整数感"的位置突变，先怀疑算术，不要怀疑物理。

这条判据的适用范围比 DSI 宽得多：PLL 分频、DMA 长度、缓冲区对齐、字节宽度，
凡是黑盒内部有整数除法或取整的地方，都可能出现这种"不该有的突变"。

## 五、我反复上当的三种模式

这部分是给自己看的，也是最该记住的。

### 1. 数值巧合

- "hline 推算 5.1 条斜线，你看到 5 条" → 后来证明 hline 根本不是主因
- "每行滑掉一个 byte-clk = 0.43px，观测 0.49px" → 但在正常配置上同样算得出 0.45px
- "VFP=22 的误差 3.45% ≈ 观测斜率 3.1%" → 但误差更大的 21 反而是正常的

**每次都对得很漂亮，每次都是巧合。**

判据：一个解释如果**只对了一个数据点**，几乎肯定是巧合。
真正的机制应该能同时解释**多个**观测。

### 2. 反相关被忽略

有三到四次出现同一个现象：

| 我优化的量 | 21（正常） | 22（异常） |
|---|---|---|
| hline 截断误差 | 更大 | 更小 |
| host/bridge 行时间失配 | 更大 | 更小 |
| FIFO 水位偏离 | 更大 | 更小 |

**我一直在优化的那个量，在"正常"的那一侧反而更差。**

这就是最明确的信号：**因变量选错了。**
物理系统通常"越准越好"，一旦出现"越准越坏"，说明真正起作用的变量在**另一个维度**上
（这里是"取整是否为整数"，不是"数值精度"）。

**这个信号出现了三次，我三次都绕过去了。** 这是本次最大的方法论失误。

### 3. 无效实验当否定证据

第 1 轮 burst 实验：改了之后没变化，我判定"burst 不是原因"。
但更可能的情况是**改动根本没生效**（写寄存器时机不对）。

`改了没变化` ≠ `假设被否定`。前者包含两种可能，不区分就下结论，等于自己骗自己。

## 六、还有一招是用户一开始就埋下的

用户在自己的诊断提交里加了一个开关：

> 「诊断: 加 DSI bridge 彩条开关，用于劈开显示故障域」

用芯片自带的 VPG 图案生成器出图，**绕开 framebuffer、DMA、bridge 的数据通路**。

一按下去：
- 图案干净、笔直、无扭曲
- 而且显示的是 8 级灰度竖条（BER 图案），颜色也对

**一次实验，把"面板 / PHY / 初始化序列 / COLMOD / lane 数 / sync 极性 / host 全套时序寄存器"
整块排除掉了。**

故障域瞬间从"整条链路"缩到"bridge 的 DPI 写入侧"。

这比任何假设检验都高效，因为它不是"猜一个机制然后验证"，
而是**用一个已知正确的信号源把系统切成两半，直接看问题在哪一半**。

> **优先找旁路，而不是优先找假设。**

---

## 七、能带走的东西

如果只留五句话：

1. **先测绘，再理论。** 单轴扫描的成本常常低于一次精确假设，信息量却高一个数量级。
2. **每个实验必须自带生效旁证。** 否则空结果不可解释，等于白做。
3. **整数边界突变 → 先查算术。** 物理不会在 21/22 之间跳，整数除法会。
4. **反相关是签名。** 优化越久越糟，说明因变量选错了，该换维度。
5. **找旁路切系统。** self-test、known-good 通路、bypass 开关，比假设更值钱。

再加一条关于协作的：

6. **昂贵的实验交给有全局视图的人做。** 这次两次关键突破都来自用户：
   一次是扫描（他知道单次实验多贵），一次是约束（他知道问题的物理结构）。
   我擅长的是从数据里挖模式和做算术——但前提是有人给出好的数据。

---

## 八、为什么这份东西不该做成 skill

说过一次，这里再说清楚。

上面那些句子，**单独拿出来都是对的，也都很容易被滥用**。

- "先测绘再理论" —— 如果问题已经有明确的、便宜的判据，扫描是浪费
- "反相关是签名" —— 如果只是测量噪声，反相关毫无意义
- "整数边界优先怀疑" —— 如果系统里根本没有整数除法，这条是干扰

**这些判据的适用性依赖于对成本的判断、对系统的物理直觉，
而这些恰恰是新手（或智能体）最缺的部分。**

把它们作为高权重提示词注入，会得到一种危险的效果：
看起来很有章法，实际在错误的地方用对了方法。

**方法论应该从具体事实里自己长出来。**
所以与其加载这份文档，不如去读 `esp32p4-dsi-debug`——
那里全是可验证的具体事实：哪个寄存器、哪个量会截断、什么现象对应什么机制。
把那些事实吃透，方法论自然会形成，而且是自己长出来的、带边界条件的那一种。
